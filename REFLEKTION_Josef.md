# Individuell reflektion - Josef Alhusseini

### 1. Din roll i teamet
Under den här sprinten hade jag huvudansvar för själva applikationen och containeriseringen. Jag satte upp vårt .NET 8 Web API i `src/Api/Program.cs` och skapade en multi-stage `Dockerfile` för att bygga och köra containern. Jag byggde alla fyra endpoints som krävdes för Certify AB (`POST /certificates`, `GET /certificates/{id}`, `GET /verify/{uuid}` och `GET /certificates`), plus vår health check på `/health` och Swagger UI. Jag löste också kopplingen till Azure Blob Storage med `Azure.Storage.Blobs` och `Azure.Identity`. Jag såg till att vi använder `DefaultAzureCredential()` så att vi slipper hårdkodade nycklar eller anslutningssträngar, och konfigurerade så att Storage-kontot och API-nyckeln läses in via miljövariabler i Container Apps.

### 2. Det svåraste momentet
Det som tog längst tid att fatta och lösa var varför verifieringslänken skapades med `http://` istället för `https://` när vi anropade `POST /certificates`. Vi körde ju mot en säker Container App-adress, men länken som kom tillbaka blev ändå http. Det visade sig bero på att TLS termineras i ingress-proxyn i Container Apps. När anropet skickas vidare internt till containern på port 8080 ser appen det som vanlig HTTP (`context.Request.Scheme` blev http). Jag testade först att trixa med forwarded headers, men det enklaste och mest stabila var att helt enkelt tvinga `https://` när vi sätter ihop `verificationUrl` i koden. Det löste problemet direkt och gjorde att alla länkar fungerar som de ska.

### 3. Vad förstår du nu som du inte förstod innan?
Tidigare visste jag bara att Managed Identity var ett smidigt sätt att slippa lösenord, men nu förstår jag hur det faktiskt hänger ihop bakom kulisserna med RBAC i Azure. Vår Container App får en systemtilldelad identitet i Entra ID, och genom att ge den rollen Storage Blob Data Contributor kan appen hämta en kortlivad token direkt från Azure-plattformen via `DefaultAzureCredential()`. Plattformen sköter all rotation och autentisering automatiskt, vilket gör att vi inte behöver spara en enda hemlighet eller anslutningssträng i git eller i någon pipeline.

### 4. Vad skulle du göra annorlunda?
Om vi skulle göra om sprinten från början hade jag sett till att vi satte upp miljövariabler och parameterstyrning ordentligt från dag ett. Under utvecklingen hade jag en tillfällig fallback i koden för `ADMIN_API_KEY` för att snabbt kunna testa lokalt. Det fungerade bra i stunden, men ledde till att vi behövde gå in och refaktorisera koden i efterhand för att rensa bort nyckeln och synka med Container Apps. Nästa gång sätter jag upp en lokal `.env`-fil eller `appsettings.Development.json` direkt.

### 5. Arkitektur och ekonomi
Lösningen för Certify AB kostar cirka 20 till 25 kronor i månaden vid lansering med 40 kunder och runt 8 000 certifikat. Vi kör på serverless-tjänster med Container Apps Consumption och Blob Storage LRS, vilket gör att vi knappt betalar någonting när systemet inte används, och vi ryms gott och väl inom Azures fria månadskvoter.

Den mest sårbara delen är den öppna verifieringslänken (`GET /verify/{uuid}`). Om någon delar sitt certifikat och det blir viralt med tiotusentals klick på en dag kommer containrarna att skala upp, vilket drar igång fler instanser och fler anrop mot storage. För att skydda systemet inför en riktig produktion bör vi sätta upp en CDN-caching framför verifieringen, till exempel Azure Front Door. Eftersom certifikaten aldrig ändras efter att de skapats kan svaret cachas helt på nätverkets kant, så att nästan inga anrop ens behöver nå vår server.
